Most integrations are built with a coding agent in the loop today. The Seyd
**skill** is the document you hand that agent: what Seyd is and is not, the
parts every integration has, which form factor fits where your encoded
frames are, the publisher contract your encoder must meet, enrolment and
access, the pilot page, the network, and how to verify the result. It
follows the [Agent Skills](https://agentskills.io) format (a `SKILL.md` with
front matter plus a `references/` folder), which Claude Code and a growing
number of agents load on their own.

With it installed, you say

> I want to integrate my robot with Seyd.

and the agent reads your codebase for what it can learn there (an RTSP URL,
a GStreamer pipeline, a ROS 2 package, an existing web app), interviews you
for what it cannot (what your encoder can change at run time, what "safe"
means when the driver vanishes, who the pilots are, how the robot reaches the
internet), chooses the form factor, writes an integration plan with every
part filled in, and only then builds and verifies it against the ladder in
the skill. The questions it asks are the ones a Seyd engineer would ask; the
rules it enforces are the ones on these pages.

Anything you would say to a colleague who knows Seyd. These are the shapes

The first is for getting to know Seyd: the agent explains the product in its
own words, then puts the public demo robot in a page and drives it, which is
the five-minute quickstart done for you. The second is the real thing: the
agent reads the rover's repository, finds the RTSP pipeline and the UDP
command path, proposes the daemon, asks the questions it cannot answer from
the code (what the encoder can change at run time, what "safe" means when
the driver vanishes, who the pilots are, what the 4G router allows), and
writes the plan before it writes code. The rest are what the same agent does
on day two: a second robot with a different form factor, the pilot page in
your own web app, a connection that fails from one network, a review of an
existing setup against the publisher contract, and the verification ladder
with numbers.

## Install it

**Claude Code.** Skills live in `.claude/skills/<name>/` in a project, or in
`~/.claude/skills/<name>/` for every project. This fetches the current skill
from this site into the project you are in:

```bash
BASE=https://seyd-signal-flj7s44j4a-ew.a.run.app/docs/skill
mkdir -p .claude/skills/seyd && cd .claude/skills/seyd && \
curl -fsSL "$BASE/files.txt" | while read -r f; do
  mkdir -p "$(dirname "$f")" && curl -fsSLo "$f" "$BASE/$f"
done
```

Self-hosting the cloud? Replace the origin in `BASE` with your own; the
skill is served at `/docs/skill/` of every deployment.

**From a checkout.** The skill is `skills/seyd/` in the Seyd repository:
`cp -r seyd/skills/seyd .claude/skills/`.

**Other agents.** Any agent that reads the Agent Skills format takes the same
folder. One that does not can be handed `SKILL.md` as context; it points at
the reference files by name, so include them.

## It is kept current with the code

The skill is a public surface of Seyd, like `seyd.h` or the `seydd.toml`
reference, and it is held to the same rule: no public surface changes
without the documentation changing in the same commit. Two of its references
are generated from the code (`seydd-config.md`, every key of the daemon's
configuration; `qos-profiles.md`, every number of the three profiles), and
every build of this site runs `tools/docs/gen-skill.py --check`, which fails
if a function, callback, element attribute, session event, agent event,
publisher-control message or failure class exists in the code and is not
mentioned in the skill, if the skill names a file or a documentation page
that no longer exists, or if a generated reference is stale. The copy you
download from this site is therefore the one that matches the code these
pages were built from.
