The C ABI is the boundary every non-Rust form factor sits on ([ADR 0004](/docs/reference/adr/0004-c-abi/)). `sdks/c/include/seyd.h` is generated by cbindgen from `packages/seyd-ffi` and is checked in, so a C consumer needs no Rust toolchain once the library is built. Any language with a C FFI can use the header today; the Python SDK is one such consumer. C++ and ROS 2 wrappers are planned, not built.

## Build and link

```bash
cargo build -p seyd-ffi --release   # target/release/libseyd.{dylib,so,a}
make -C sdks/c check                # builds and runs the ABI conformance test
make -C sdks/c                      # builds every example into sdks/c/build/
```

Link against `libseyd` (cdylib) or `libseyd.a` (staticlib). The library pulls in the platform's TLS, threading and network libraries, and the `Makefile` is the authoritative per-platform list:

```makefile
CFLAGS  += -std=c11 -Wall -Wextra -O2 -I include
ifeq ($(OS),Windows_NT)
    LDFLAGS += $(TARGET)/seyd.dll
else ifeq ($(UNAME),Darwin)
    LDFLAGS += -L $(TARGET) -lseyd -framework CoreFoundation -framework Security -framework SystemConfiguration
else
    LDFLAGS += -L $(TARGET) -lseyd -lpthread -ldl -lm
endif
```

On Windows the library is `target/release/seyd.dll` (plus `seyd.dll.lib` for MSVC and the static `seyd.lib`). With MinGW gcc, name the DLL as an input file rather than `-lseyd`: ld would otherwise find the static `seyd.lib` first, whose MSVC objects it cannot link. The Makefile runs under GNU make with MinGW gcc, which is what CI does in an MSYS2 shell, and the two examples build there unchanged. Put the directory holding `seyd.dll` on `PATH` to run them.

At run time the dynamic library must be findable: the Makefile sets `DYLD_LIBRARY_PATH` or `LD_LIBRARY_PATH` to the target directory when it runs the check.

## The lifecycle

The header's own summary, in order:

```
seyd_agent_create -> seyd_channel_add* -> seyd_agent_start
  -> seyd_push_frame / seyd_push_message
  -> seyd_agent_stop -> seyd_agent_destroy
```

- `seyd_agent_create` takes a `seyd_config` and a `seyd_callbacks` and does no network work. Strings are borrowed for the call only; Seyd copies what it keeps.
- `seyd_channel_add` is valid only before start. Channels are numbered from 1 in the order added, and that numbering is what the pilot sees.
- `seyd_agent_start` binds, discovers candidates and announces. It blocks until the robot is announced, up to a second or two. Callbacks begin after it returns `SEYD_OK`.
- `seyd_agent_stop` tears down sessions and blocks until the callback thread has finished, so no callback runs after it returns. `seyd_agent_destroy` stops if running and frees the handle.

Every fallible call returns a `seyd_status`; `SEYD_OK` is zero.

## The example: a sensor robot in one file

`sdks/c/examples/sensor-robot.c` announces itself, publishes a counter on a sensor channel at 10 Hz and prints whatever a pilot sends on the command channel. It is built by `make -C sdks/c`, so the page cannot show code that does not compile.

Walking through it:

- **Callbacks** come first. Each prints and returns; `on_session_ended` is where a real robot parks its actuators, `on_requested_config` where it reconfigures its encoder. `on_signal_state` reports connected, disconnected or denied, and the robot is unreachable while signaling is down.
- **`seyd_init_logging("info")`** installs a stderr log filtered by a directive such as `info` or `seyd_core=debug`. Optional, at most once, before creating an agent.
- **`seyd_config`** sets the robot id, the signal URL and the credential path from `argv`; a zero `quic_port` or `max_sessions` and a NULL `qos_profile` take the same defaults as `seydd.toml` (4433, 4, `balanced`).
- **`seyd_channel_add`** twice: a `telemetry` sensor channel and a `drive` command channel. The id written to `out_channel_id` is what `seyd_push_message` takes.
- **`seyd_agent_start`**, then the main loop pushes a JSON counter once every 100 ms until SIGINT.
- **`seyd_counters`** on the way out snapshots the engine counters; `seyd_agent_destroy` releases everything.

## Adding video

Add a video channel with a WebCodecs codec string and the nominal frame rate, then hand it one encoded access unit per call:

```c
uint8_t video;
seyd_channel_config vc = {.kind = SEYD_CHANNEL_VIDEO, .name = "main",
                          .codec = "avc1.42001f", .fps = 25};
seyd_channel_add(agent, &vc, &video);

seyd_agent_start(agent);
for (;;) seyd_push_frame(agent, video, au, au_len, is_idr, capture_ts_us);
```

`seyd_push_frame` never blocks. A frame that arrives while the previous one is still going out is dropped by admission control and counted in `frames_dropped_backlog`; keyframes are never dropped. `capture_ts_us` is the source's capture clock and travels to the pilot, which paces presentation on it ([ADR 0005](/docs/reference/adr/0005-presentation-pacing/)), so pass the encoder's timestamp rather than "now". Seyd is handed encoded access units and relays them; it never decodes, re-encodes or inspects them, and whatever your encoder produced is what the pilot decodes. What the encoder must do is on [The publisher contract](/docs/robot/publisher-contract/) and [Encoder setup](/docs/robot/encoder-setup/). Where the publisher can encode the same picture more than once, declare layers; see [Simulcast](/docs/robot/simulcast/).

Set `on_requested_config` and `on_recovery_request`. The first carries Seyd's targets as the `video-config` JSON (`maxBitrateKbps`, `latencyBudgetMs`, `maxGopMs`, `preferIntraRefresh`, `suggestedFps`, `reason`); the second names the recovery point a pilot needs (`ltr`, `intra_refresh` or `idr`). Keyframes are on demand ([ADR 0009](/docs/reference/adr/0009-keyframes-on-demand/)): honour the request and treat `maxGopMs` as a long ceiling, not a cadence.

## Threading and error rules

- **Callbacks run on one dedicated Seyd thread and must not block.** A slow callback delays every later event. Queue the work and return. Pointers passed to a callback are valid only for the duration of the call.
- **`seyd_push_*` never blocks** and may be called from any thread.
- **Check `seyd_last_error()`** after a non-`SEYD_OK` status. It is thread-local and valid until that thread's next failing call; never free it.
- **`SEYD_ERR_STATE`** means a call in the wrong lifecycle state, such as `seyd_channel_add` after start. **`SEYD_ERR_BACKPRESSURE`** is reserved and not returned: the engine drops under pressure by design and reports it through the counters.
- **The ABI is versioned.** Compare `seyd_abi_version()` with the `SEYD_ABI_VERSION` you compiled against. Additions are appended, never reordered, until the version is bumped.

## Checking the ABI

```bash
make -C sdks/c check
```

`examples/abi-smoke.c` is the conformance test: header matches library, channel numbering, lifecycle enforcement, argument validation. No network. Run it whenever the library or the header changes.

The [C ABI reference](/docs/reference/c/) lists every status code, struct, callback and function, generated from the header.
